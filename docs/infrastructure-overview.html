The stack, in plain language

If Kubernetes, Helm and GitOps are new to you, read this section first. It builds the stack from the bottom up and says what each layer is for, not how to operate it. The rest of the page assumes you have read it, and the glossary at the end defines every term the page uses.

  1. Eight small programs, together making one application
    Each service does a single job: one serves configuration, one is the phone book the others use to find each other, one takes web requests, and the rest hold the actual data. They are ordinary Java programs — nothing about them knows they are going to run in a cloud.
  2. Containers — a program frozen together with everything it needs
    A container image is a program plus its exact runtime and settings, packaged into one file. A container is that image running. The point is that it behaves the same on a laptop and on a server, because it carries its own environment with it. Images here are built by GitHub and stored in ECR, Amazon's image warehouse — one repository per service per environment, so a dev image can never be mistaken for a prod one.
  3. Kubernetes — a pool of machines you describe a desired state to
    A cluster is a group of machines that Kubernetes treats as one pool. You do not say "run this on machine 2"; you say "keep two copies of vets-service running and healthy", and Kubernetes works continuously to make that true and keep it true. EKS is Amazon's managed version: AWS runs the control plane, you supply the machines. A namespace is a folder inside the cluster that stops names colliding — here one per environment, so dev and prod are the same chart with the same names in different boxes.
  4. Helm — one template, eight sets of answers
    Kubernetes is configured with YAML files, and eight services across two environments would mean a great deal of near-identical YAML. Helm is a template engine for exactly that: one chart holds the shape, and a small values file per service supplies what differs — its port, its environment variables, what it must wait for. This repo has exactly one chart and uses it sixteen times.
  5. GitOps — the repository is the truth, and a program enforces it
    The older way to deploy is for a person or a CI job to run kubectl apply against the cluster, which leaves nobody able to say what the cluster should contain. GitOps replaces that with a rule: Git says what should be running, and a program inside the cluster keeps reality matching it. That program is ArgoCD. It polls this repository, notices a changed image tag, and applies it — which is why no step in either pipeline ever runs kubectl.
  6. Terraform — everything underneath the cluster, described as code
    The network, the machines, the database, the image warehouse and the DNS records are not created by hand. Terraform reads .tf files describing the resources you want and makes the AWS API calls to create them. It keeps its own record of what it made in a state file, which is how it knows what to change and what to leave alone.
  7. Two repositories, one hand-off
    The application's source code lives in one repository; this infrastructure lives in another. The application repository builds images and, when it is done, sends a signal to this one. This repository writes the new tag into a values file and commits. ArgoCD sees the commit and deploys. The commit is the deployment signal — that single sentence is the whole design.

Glossary

Every term the page uses, in plain language, grouped by where it comes from, with two groups at the end that cut across the rest. Open the group you need — each entry says what the thing is and, where it matters, what it does in this project specifically.

AWS — the account, the network and the perimeter 13 terms
Region
The geographic location resources run in. Everything here is in eu-central-1 (Frankfurt), so no request crosses a continent to reach the database.
Account
The billing and permission boundary. One account, 550798137608. A resource in another account is invisible unless access is explicitly granted.
ARN
Amazon Resource Name — the full, unambiguous name of one specific resource, such as arn:aws:ecr:eu-central-1:550798137608:repository/petclinic-dev/vets-service. Every permission is written against ARNs, which is why they appear throughout the IAM policies here rather than resource names.
VPC
Virtual Private Cloud — your own private network inside AWS, with an IP range you choose. 10.0.0.0/16 in dev, 10.1.0.0/16 in prod.
CIDR notation
The /16 in 10.0.0.0/16 — how many leading bits of the address are fixed, so the smaller the number the bigger the network. /16 is 65,536 addresses, /24 is 256, and /32 is exactly one. The EKS API allowlist is a /32 because it admits a single workstation and nothing else.
Subnet
A slice of that range, pinned to one availability zone. Every subnet here is public — it has a route to the internet. That is a deliberate cost decision, and it is why the security groups carry the entire burden of access control.
Availability zone
One isolated data centre within a region. The two subnets here sit in two different zones, which is what would let the network survive one of them failing — though with a single-AZ database, dev would not survive it in any useful sense.
Internet gateway
The single door between this VPC and the public internet. Without it nothing in these subnets could be reached from outside, or reach out.
Route table
The list saying where traffic leaving a subnet should go. There is one here, and its single non-local rule sends everything out through the internet gateway — that one line is what makes the subnets public.
Security group
A firewall attached to a resource. Each rule names a source and a port; anything not named is refused. In this design they are the perimeter, rather than a second layer behind one.
ALB
Application Load Balancer — the one component that faces the internet. It terminates TLS, picks a healthy target and forwards the request.
Route 53
Amazon's DNS. It maps petclinic-dev.gannet.click onto the load balancer's address using an alias record, so the address can change without anyone editing DNS.
ACM
Amazon Certificate Manager — holds the TLS certificate that makes https:// work. Issued for *.gannet.click, so one certificate covers both environments.
AWS — the services 21 terms
ECR
Elastic Container Registry — the warehouse where built images are stored. One repository per service per environment.
Image tag mutability
Whether a tag that has already been pushed may be overwritten. Dev is MUTABLE, so a rebuilt image can reuse a tag; prod is IMMUTABLE, so a tag that exists can never come to mean different bytes than it did yesterday.
RDS
Relational Database Service — Amazon runs MySQL for you and hands back a hostname and credentials. One instance per environment, db.t4g.micro, single-AZ.
DB subnet group
The list of subnets RDS is allowed to place its instance in. RDS requires one even when, as here, there is only one possible answer.
Parameter group
The database engine's settings, held by AWS rather than in a file — petclinic-{env}-mysql8 here. Changing one is the thing apply_immediately decides the timing of: now, or at the next maintenance window.
Final snapshot
The backup RDS takes as its last act before being deleted. Dev skips it so a teardown leaves nothing behind to pay for; prod takes one, because deleting a database should not also be the end of the data.
Backup retention
How many days of automatic backups RDS keeps, and therefore how far back point-in-time recovery can reach. Seven days in dev, thirty in prod.
EBS
Elastic Block Store — the virtual disks attached to EC2 instances, and so to the worker nodes. The node group's disks are gp3, the general-purpose SSD type, and encrypted. Kubernetes cannot use EBS on its own: it needs a CSI driver, the plugin that teaches it how to create and attach a disk, which is one of the four add-ons.
IAM
Identity and Access Management — who, or what program, may call which AWS API. A role is an identity a program assumes temporarily instead of holding a password; a policy is the document listing what that role may do.
IRSA
IAM Roles for Service Accounts — the mechanism that lets one pod hold AWS permissions with no key stored anywhere. A Kubernetes service account is tied to an IAM role, and the cluster's OIDC provider is what makes that claim trustworthy to AWS. The load balancer controller, the EBS driver and External Secrets all reach AWS this way; nothing in the cluster holds a long-lived credential.
Secrets Manager
A vault for passwords and API keys. Kubernetes reads from it at runtime instead of the value being written into a file.
Recovery window
How long a deleted secret can still be restored. Dev uses 0, so a destroyed environment frees the name immediately and a rebuild can reuse it; prod uses seven days, so deleting a secret by mistake is recoverable.
CloudWatch
Amazon's logging and metrics service. Used for exactly one thing here: the EKS control-plane logs.
SNS
Simple Notification Service — how AWS sends a message somewhere when something happens, usually triggered by a CloudWatch alarm. It appears in this page only to record that there is none.
EKS
Elastic Kubernetes Service — Amazon's managed Kubernetes. AWS runs the control plane; you supply the machines.
Access entry
The modern way to grant a person or role the right to use a cluster, replacing the older ConfigMap. This cluster is configured so that even the identity that created it holds no automatic rights — an access entry is what makes kubectl work at all, which is why a green terraform apply is not by itself enough.
Node group
The set of identical worker machines Terraform manages as one unit — two of them in each environment.
OIDC
OpenID Connect — the standard that lets a GitHub workflow prove "I am this repository, on this branch" and receive a short-lived AWS credential. It exists so that no AWS access key is ever stored in GitHub.
S3
Object storage — files in a bucket, addressed by key. Used here for one thing: the bucket holding Terraform's state file.
SSE
Server-side encryption — AWS encrypting an object at rest, so the bytes on disk are unreadable without the key. Switched on for the state bucket.
DynamoDB
A managed key-value database. Used here for one thing: the lock table that stops two Terraform runs applying at the same time.
Kubernetes — the objects inside the cluster 24 terms
Cluster
The pool of machines Kubernetes schedules work onto. Two nodes per environment here.
kubectl
The command-line tool for talking to a cluster — kubectl get pods, kubectl logs. Nothing in either pipeline runs it: humans do, and ArgoCD does the equivalent from inside the cluster.
Node
One machine in that pool. Pods run on nodes.
Add-on
A component AWS installs into the cluster and keeps updated, as opposed to one installed by hand. The four here are coredns (turns a service name into an address), kube-proxy (sends traffic to the right pod behind that name), vpc-cni (gives each pod a real IP from the VPC) and aws-ebs-csi-driver (creates and attaches disks). Metrics Server is not among them, which is the whole reason the HPA cannot scale.
Pod
The smallest thing Kubernetes runs: one or more containers sharing a network address. Almost always one container here.
Deployment
The object that says "keep N copies of this pod running". If a pod dies, the Deployment replaces it.
Replica
One copy of a pod. "Two replicas" means two copies running at once.
Service
A stable name and address in front of a set of pods, so a caller never needs to know which pod is where. It is how one service finds another by name.
Namespace
A folder inside the cluster that keeps names and permissions from colliding. One per environment: petclinic-dev and petclinic-prod.
ConfigMap
Non-secret configuration handed to a container — which Spring profiles to activate, for instance.
Secret
The same idea for sensitive values. Here the value does not live only in the cluster: it is synced from AWS Secrets Manager.
ServiceAccount
The identity a pod uses when it talks to the Kubernetes API or, through a role, to AWS.
Ingress
The rule saying "a request for this hostname goes to this Service". It is what causes a load balancer to be created at all — no Ingress, no ALB.
IngressClass
The name binding an Ingress to the controller that implements it. Here: alb. An Ingress naming a class that does not exist is ignored — no error, and no load balancer.
Init container
A container that runs to completion before the main one starts. Used here to make each service wait for config-server and discovery-server.
Readiness probe
A periodic check deciding whether a pod should receive traffic. Failing it removes the pod from the Service without restarting it.
Liveness probe
A periodic check deciding whether a pod is still alive. Failing it restarts the container.
Requests and limits
The CPU and memory a container is guaranteed, and the most it may use. Requests decide where the scheduler places it; limits decide when it is throttled or killed.
HPA
HorizontalPodAutoscaler — an object that adds or removes replicas as load changes. It reads CPU usage from the Metrics Server.
PDB
PodDisruptionBudget — a rule limiting how many replicas a voluntary action, such as a node upgrade, may take down at once.
Metrics Server
The component that collects per-pod CPU and memory. Without it an HPA has nothing to read.
CRD
Custom Resource Definition — a way to teach Kubernetes a new kind of object. External Secrets and the load balancer controller each add their own set.
Operator
A program running in the cluster that watches for a custom object and makes the real world match it. External Secrets is one here: it watches for a request naming an AWS secret, and creates the Kubernetes Secret that request describes.
Pod Security Standard
Labels on a namespace that make Kubernetes reject pods asking for more privilege than the level allows. Both workload namespaces here enforce baseline.
Helm — one chart, eight releases 4 terms
Chart
A package of Kubernetes templates plus their defaults. This repo has exactly one, used by all eight services.
Values file
The small YAML that fills in a chart's blanks. One per service, plus one per environment.
Release
One installed instance of a chart. Eight services means eight releases of the same chart in one namespace.
Render
Turning a chart plus values into plain Kubernetes YAML without applying it. helm template is how this repo checks a change before committing it.
GitOps and ArgoCD 11 terms
GitOps
The practice of treating a Git repository as the source of truth for what runs in a cluster, with a program inside the cluster keeping the two in agreement.
ArgoCD
That program. It polls this repository, compares it against the cluster, and applies the difference.
Application
ArgoCD's unit of work: "this repository path, with these values files, into this namespace". Sixteen of them here.
Sync
ArgoCD applying Git's version to the cluster.
Drift
The cluster no longer matching Git — usually because somebody changed something by hand.
Prune
Deleting cluster objects that have been removed from Git.
Self-heal
Reverting a manual change back to what Git says.
Synced / OutOfSync
Whether the cluster currently matches Git. This is separate from whether the workload is working.
Healthy / Degraded
Whether the pods are actually running. A revision can be Synced and Degraded at once — that is what a failing image pull looks like.
RBAC
Role-based access control — who may do what in ArgoCD. Configured here so one group may sync dev and nobody may sync prod yet.
SSO
Single sign-on — logging in through one central identity provider rather than a password per tool. ArgoCD's RBAC file names an SSO group that has never been created, which is why it currently grants nobody anything.
CI/CD — GitHub Actions 12 terms
Workflow
One YAML file under .github/workflows/ describing work GitHub should run.
Job
A unit inside a workflow. Jobs run in parallel unless one declares it needs another.
Step
One command or one action inside a job. Steps run in order.
Runner
The machine GitHub lends a job for its duration. Nothing persists on it afterwards.
Matrix
Running the same job once per item in a list — here, once per changed service, in parallel.
Reusable workflow
A workflow another workflow can call, so the build steps are written once instead of eight times.
Artifact
A file a job produces and keeps after it finishes, such as the Trivy scan report.
Commit SHA
The unique identifier of a commit. Used as the image tag, so a running container can be traced back to exact source.
Image tag
The label on an image version. latest is avoided because it is ambiguous; a commit SHA is exact.
Trivy
A scanner that inspects an image's installed packages and reports known vulnerabilities. It fails the build on CRITICAL ones.
CVE
A publicly catalogued security vulnerability — what Trivy reports.
repository_dispatch
A GitHub event one repository can send to another. It is the only way to trigger a workflow across repositories, which is why the hand-off between the two repos uses it.
Terraform — how the AWS side is described 9 terms
Module
A reusable group of resource definitions. One per concern here: vpc, eks, ecr, rds, secrets, dns, github-oidc.
Root module
The directory that calls modules and supplies their values. terraform/environments/dev and .../prod are the two here.
Plan / apply
plan shows what would change; apply makes the change. This repo never applies without a saved plan.
tfvars
The file holding values for a particular run. Gitignored here, because it holds a real workstation IP and a real API key.
Provider
The plugin that knows how to talk to a given API. Only aws and random are used, which is why Terraform never needs cluster access.
State file
Terraform's own record of what it created, and the only reason it can tell a change from a creation. Kept in S3 rather than on a laptop, so any machine can run the next apply.
State key
The path of one environment's state file inside that bucket — petclinic/dev/terraform.tfstate. One key per environment is what stops dev and prod from ever sharing a state file.
State lock
A marker Terraform takes while it runs, so two applies cannot interleave and corrupt the file. Held in DynamoDB here.
Bootstrap
The setup that must exist before Terraform can run at all — here the state bucket and the lock table, created once by scripts/bootstrap-state.sh rather than by Terraform itself.
Building for ARM — why every image is arm64 5 terms
CPU architecture
The instruction set a program is compiled for. An image built for one architecture will not start on the other — this is not a speed difference but a hard incompatibility, which is why the target architecture is a build-time decision and not a runtime one.
arm64
The 64-bit ARM architecture. Every image in this project targets linux/arm64 and nothing else, because every node is ARM.
Graviton / t4g
Amazon's own ARM server chips. The g in t4g.medium and db.t4g.micro means Graviton, and that is the reason the whole project is ARM: Graviton instances cost less per hour than the Intel equivalents. It is a deliberate choice with a consequence, which the next two entries describe.
QEMU
An emulator that lets a machine of one architecture run code built for another. GitHub's runners are x86 and the target is ARM, so the build step installs QEMU first and the whole Maven build then runs emulated — slower than native, and the price of producing ARM images without an ARM runner.
buildx
The Docker plugin that can build for an architecture other than the host's. It is what consumes QEMU and produces the linux/arm64 image.
The application — Spring Boot and Java 7 terms
Spring Boot
The Java framework the eight services are written in. It supplies the web server, the health endpoints and the configuration loading, so each service is a little code plus a lot of convention.
Spring profile
A named switch that changes which settings load. docker makes a service read its configuration from the config server; mysql makes it talk to RDS instead of an in-memory database. A service runs with a list of them, and the list differs by service.
Actuator
Spring Boot's built-in management endpoints. /actuator/health/readiness and /actuator/health/liveness are not code anyone here wrote — they come free with the framework, and they are what the Kubernetes probes call.
JVM
Java Virtual Machine — the program that runs compiled Java. It matters operationally because it holds a large fixed footprint: roughly 350 MiB resident, against a 128 MiB request. That gap is what once let the scheduler pack four services onto one node and take it down.
JDK / Temurin
The Java Development Kit — compiler and runtime together. Temurin 17 is Eclipse's free build of it, and it serves as both the build image and the runtime base here.
Maven / mvnw
The build tool that turns Java source into a runnable jar. mvnw is its wrapper script, committed alongside the source so the build uses the pinned version rather than whatever happens to be installed on the runner.
Caffeine
An in-memory cache for Java. vets-service keeps its vet list in one, so repeated reads do not each become a database query.

What exists, and how a request reaches it

One request path from the internet to the database, with the security group and port on every hop. Everything sits in public subnets — the groups are the perimeter, not the subnet layout.

The path from a commit to a running pod

Two repositories and three systems. The app repo builds and pushes; this repo only ever commits a tag; ArgoCD does all the deploying. No step in either pipeline runs kubectl or helm upgrade.

  1. A commit lands on main of the app repo
    truongnvnse/spring-petclinic-microservices — Java source only. The workflow has no paths: filter on its trigger, so every push starts the run; the filtering happens in the first job.
  2. changes job decides what is worth building
    dorny/paths-filter maps each of the eight services to spring-petclinic-{service}/**. A change to pom.xml, docker/**, mvnw or .mvn/** matches the shared filter and selects all eight instead. Output is a JSON array of short service names.
  3. build job runs once per selected service, in parallel
    A matrix over that array calls the reusable build-image.yml: Temurin 17, then QEMU + buildx, then ./mvnw -B -pl spring-petclinic-{service} -am package -DskipTests produces the jar and a linux/arm64 image from docker/Dockerfile. Tests do not run here — maven-build.yml owns them, so a green image build is not a green test run. Trivy runs twice — a CRITICAL,HIGH report that never fails, and a CRITICAL-only gate that blocks the push.
  4. The image is pushed to ECR
    550798137608.dkr.ecr.eu-central-1.amazonaws.com/petclinic-dev/{service}:{7-char SHA} — the tag is the commit, never latest. Auth is OIDC: the job assumes a role via a short-lived token, never a stored access key.
  5. dispatch job fires an event at this repo
    repository_dispatch type app-image-built, payload {"sha":"…","services":"vets-service visits-service"}. workflow_run cannot be used here — it only fires for workflows in the same repository, and the build ran in the other one.
  6. update-image-tags.yml writes the tag into Git
    Validates the payload against a hardcoded allowlist of the eight services, then one yq call per file: helm-values/{service}.yaml gets the new image.tag. Commits as github-actions[bot]. Only the services in the payload are written — most dispatches name a subset, because most builds are a subset.
  7. ArgoCD sees the commit and syncs
    One Application per service per environment, all pointing at helm/petclinic-service with that service's values file plus the environment overlay. ArgoCD watches the repository itself, not Actions events — which is why a push made with GITHUB_TOKEN, which triggers no workflows, still deploys.
  8. The Deployment rolls out
    Helm renders the chart and ArgoCD applies it. New pods pull the new tag, pass readiness on /actuator/health/readiness, and the old ones are retired.

The AWS layer

Seven Terraform modules, called from one root module per environment. Every resource is named petclinic-{env}-{resource}, with two deliberate exceptions: the cluster and its node group are named for the environment alone, so they read petclinic-dev and petclinic-dev-nodes rather than carrying an -eks suffix.

ModuleWhat it ownsWhat it creates
vpc The network and the perimeter VPC 10.0.0.0/16, two public subnets, an internet gateway, one route table, four security groups and all fourteen of their rules
eks The cluster, the nodes, the add-ons, and every role the cluster runs as petclinic-{env}, node group petclinic-{env}-nodes, a cluster OIDC provider, five IAM roles, four managed add-ons, one log group
ecr One image repository per service Eight repositories named petclinic-{env}/{service}, each with a two-rule lifecycle policy

secrets The one secret Terraform writes by hand petclinic/{env}/openai-api-key

github-oidc The role GitHub Actions assumes The account's OIDC provider (dev only) and petclinic-{env}-github-actions-role with a push-only ECR policy

Prod calls five of the seven. There is no module "dns" and no module "github_oidc" in the prod root — prod has no certificate, no hostname, and no CI role of its own. A further two module directories exist and are comment-only stubs: modules/karpenter is reserved for the scaling story, and modules/observability records that the observability stack was deliberately moved in-cluster, so no Terraform resources are planned for it.

Cluster access is by access entry, not by ConfigMap. The cluster runs authentication_mode = "API_AND_CONFIG_MAP" with bootstrap_cluster_creator_admin_permissions = false, so the identity that created it holds no implicit rights — an aws_eks_access_entry with AmazonEKSClusterAdminPolicy is what grants admin, and that is what the admin principal ARN list drives. The role that runs the cluster is separate from the role that administers it, which is why a green terraform apply does not by itself mean kubectl will work.

The chart

The release name is the object name. The chart's fullname helper returns the release name rather than the usual chart-release concatenation, which is why ArgoCD sets releaseName: vets-service with no environment suffix and why the values files set fullnameOverride — the environment lives in the destination namespace, not in the object name. Two guards are worth knowing: the pod template carries a checksum/config annotation so a ConfigMap change restarts the pods, and configmap.yaml fails the render outright if a service asks for SPRING_DATASOURCE_URL while the environment overlay left database.connectionString empty — which is what catches a service file rendered against the wrong overlay.

The two differ structurally, and getting it wrong fails quietly in one direction. Adding a property to the OpenAI secret fails at sync because the value is not JSON. Removing it from the RDS secret does not fail — it copies the whole {"username":…,"password":…} blob into both keys. Both objects refresh hourly and sit behind one ClusterSecretStore named aws-secrets-manager, which is scoped by a namespace regex to exactly petclinic-dev and petclinic-prod — a Secret in any other namespace cannot be resolved through it. Authentication is IRSA, so no AWS credential exists anywhere in the cluster.

The value-file order is the merge order — service file first, environment overlay second, so the overlay wins on anything both set. That is what lets dev.yaml turn a service's HPA off without editing the service file. It is also why dev.yaml cannot set replicaCount: as the last layer it would beat every per-service value, including the replicaCount: 1 that admin-server needs in prod. Things that will surprise you

Each of these has bitten someone, or would. They are the parts of the design that are not visible from a file listing.

  • !Dev owns the account-global OIDC provider. An AWS account may hold only one provider per URL, so this per-environment module creates a resource that is not per-environment. Destroying dev removes it, and a future prod pipeline would stop being able to assume its role until dev is re-applied. Prod has no github_oidc module at all today — adding one means create_oidc_provider = false plus dev's provider ARN passed in, not flipping a flag on an existing call.
  • !The ALB is not in Terraform state. It is created by the AWS Load Balancer Controller in response to the Ingress, so terraform destroy does not know it exists — and EKS teardown fails with five DependencyViolation errors at once (two subnets, the certificate, the security group, the gateway). Those five errors are one orphaned ALB. Delete the Ingress first and wait for it to go.
  • !The Ingress is a template, and a stale one applies cleanly. ingress.yaml.tpl holds <ACM_CERTIFICATE_ARN> and <ALB_SECURITY_GROUP_ID>; both are regenerated on every rebuild. A rendered file holding last rebuild's values is still valid YAML, so kubectl apply succeeds and the failure only surfaces later as a controller reconcile error.
  • iDev runs t4g.medium, not the spec's t4g.small. This is a measured correction, not a preference. t4g.small allows 11 pods per node, so two nodes give 22 slots against 23 needed once the system pods are counted — the eighth service sat Pending. It also reports 1365 MiB allocatable, and a Spring Boot service holds ~350 MiB resident against a 128Mi request, so the scheduler packed four JVMs onto one node and the kubelet stopped posting status. Prod is still on t4g.small and will need the same fix before its first deploy.
  • iMost dispatches write fewer than eight files. The build only builds changed services, so the payload names a subset and update-image-tags.yml writes only that subset. A commit touching one values file is the normal case, not a bug — and it is what keeps helm-values/ and ECR in agreement.
  • iArgoCD Synced does not mean healthy. status.sync means the cluster matches Git; status.health means the pods actually run. A revision can be synced and degraded at the same time — that is what an ImagePullBackOff looks like in the ArgoCD UI.
  • !Prod is a specification, not a running environment. Five things are missing before its first sync can succeed, and each fails differently. The prod Applications have never been applied. helm-values/prod.yaml still holds a deliberately unresolvable RDS hostname (REPLACE-ME-prod-rds-endpoint…), so the pods would die on UnknownHostException. The petclinic-prod ECR repositories have never been created — terraform/environments/prod/ has not been applied. No prod Ingress exists — the template has only ever been rendered for dev. And both ExternalSecrets hardcode namespace: petclinic-dev, so installing them into petclinic-prod would leave SPRING_DATASOURCE_PASSWORD and OPENAI_API_KEY pointing at Secrets that do not exist there — CreateContainerConfigError on every pod, from a file that looks correct.
  • iDev is destroyed and rebuilt on a cycle. That makes an empty state and a full-create plan the normal case rather than a lost state file. Three settings exist only to survive that: force_delete on the ECR repositories, skip_final_snapshot on RDS, and secret_recovery_window_in_days = 0 on both Secrets Manager and RDS — a 30-day recovery window would block re-creating the same secret name on the next rebuild.
  • iOnly aws and random providers are used. Terraform never talks to the Kubernetes API, so a teardown never needs cluster access — and kubectl failing does not mean Terraform will.

What this document does not cover

Everything above is real. This section is the boundary of the drawing — the things a reader could reasonably assume exist because a platform usually has them, and that this one does not have yet. Read it before concluding something is missing from the page rather than from the repo.

  • !There is no observability at all. No CloudWatch alarms, dashboards or SNS topics; no Prometheus, Grafana, Loki, FluentBit or Zipkin; no cost budget. The only monitoring resource in the entire repository is a single CloudWatch log group for the EKS control plane (terraform/modules/eks/main.tf). terraform/modules/observability/ exists but is a deliberately empty placeholder — its own header says the stack is meant to run in-cluster rather than as Terraform resources, and none of it has been installed. An alarm that never fires and a page that never arrives look identical to a healthy system.
  • !The HPA cannot scale, and does not say so. The chart renders hpa.yaml and the values files configure it, but the cluster has no Metrics Server — the four managed add-ons are coredns, kube-proxy, vpc-cni and aws-ebs-csi-driver. An HPA in that state reports <unknown>/70% and never scales; it does not error. hpa.yaml says this in its own header (PETPLAT-72). Dev is unaffected in practice because dev.yaml turns autoscaling off — but prod is configured to scale and will not.
  • !Nothing tells a human that prod is waiting. The ArgoCD notifications controller is deployed, but its ConfigMap has no data — no triggers, no subscriptions, no notifier. There is no Slack, email or webhook integration anywhere in the repo. A prod Application sits OutOfSync until somebody opens the ArgoCD UI and looks.
  • iThere is no ResourceQuota and no LimitRange. The chart renders six kinds and neither of these is one of them; the only mentions in the repo are unimplemented backlog stories. Per-container requests and limits are set, so the scheduler behaves, but nothing caps what a namespace can consume in total.
  • iThere is no ApplicationSet. The sixteen Application objects are sixteen hand-written files. The ApplicationSet controller ships with the ArgoCD install and is running unused. Adding a ninth service means writing two more files by hand, not editing a generator.
  • iThe state bucket and lock table are not in Terraform. petclinic-terraform-state-550798137608 and petclinic-terraform-locks appear in the architecture figure as supporting services, but nothing in terraform/ creates them — they cannot be, since Terraform needs them to run. scripts/bootstrap-state.sh creates both, with versioning, SSE, a public-access block and an HTTPS-only bucket policy. It is the only script in scripts/ that provisions AWS resources, and it runs once per account.
  • iThere is a cheaper alternative to destroying dev. scripts/stop-env.sh scales the node group to zero and stops RDS, leaving the control plane up; start-env.sh reverses it. This page describes the destroy-and-rebuild cycle because that is what the state usually reflects — but a plain terraform apply silently undoes a stop, because Terraform still declares min 2 / desired 2 and will put the nodes back.
  • iThis page describes infrastructure, not the tooling around it. The .claude/ directory (hooks, path-scoped rules, review subagents, skills), most of scripts/ beyond the ones named inline, and docs/jira-backlog.md are all real and all outside the scope of this document. The Jira backlog in particular is where the work behind the gaps above is tracked.
